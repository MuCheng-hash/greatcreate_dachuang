## Context

首版跨会话记忆使用同一 SQLite 文件保存 `pending`、`active` 和 `deleted` 三种状态。旧仓库在任意激活入口调用 `_delete_field_conflicts`，使同字段的活跃值自动进入回收站。前端确认成功后只替换候选自身，未获得旧项变更结果，因此内存列表会在刷新前保持陈旧。

本变更不改变账号和学校双重隔离、敏感信息过滤、30 天回收站、审计无正文和历史记录恢复边界。

## Goals / Non-Goals

**Goals:**

- 让所有同字段激活入口先检测冲突，再以明确决策完成状态迁移。
- 以同一 SQLite 事务完成冲突校验、旧项回收、新项激活和无正文审计，避免并发覆盖。
- 让聊天页和个人中心展示一致、可解释且不依赖刷新修正的结果。
- 把 `response_format` 和 `answer_format` 视为同一核心画像字段。

**Non-Goals:**

- 不对自定义无字段记忆做语义相似度合并。
- 不新增数据库表、向量召回、RAG 或浏览器可控的作用域参数。
- 不批量修改既有历史记忆；别名仅在读取、比较和新写入时规范化。

## Decisions

1. **冲突键。** 仅当记忆拥有相同 `ownerId + scopeType + scopeId + normalizedFieldKey`、处于 `active`、且不是当前条目时才构成冲突。`response_format` 在所有比较和写入边界规范为 `answer_format`。没有字段键的自定义记忆继续使用正文完全相同的幂等判断。

2. **预检先于决定。** 新增内部和 Spring 同源的 `GET /api/ai/memories/{id}/confirmation-preview`。它按登录态范围返回候选、冲突项摘要与 `duplicate`；不改变状态。完全重复表示已有同字段同内容的活跃值，用户无需再次产生有效记忆。

3. **确认的显式语义。** `POST .../confirm` 可选接收 `replaceConflicts`。无冲突时直接确认；完全重复时将候选移入回收站并返回已存在结果；有冲突但未传 `replaceConflicts=true` 时返回 HTTP 409、包含预检数据且不修改数据库；明确替换时在同一事务中把所有冲突项移入 30 天回收站、激活候选并写不含正文的审计。

4. **其他激活入口。** 恢复、手动新增为 active、编辑为 active 或改变字段键时共享冲突检测。因为这些入口没有可确认的候选卡片，后端以稳定的 409 冲突响应拒绝静默覆盖；前端在个人中心复用冲突弹窗并在用户选择替换后重试携带 `replaceConflicts=true` 的请求。

5. **保留旧值与取消。** 对聊天页的待确认候选，选择“保留旧值”调用现有回收接口，将候选移入回收站；取消、Esc 或点击遮罩不发写请求，候选保持 `pending`。对个人中心新增/编辑的未持久化操作，取消只关闭弹窗，原表单内容保留供用户修改。

6. **前端一致性。** 成功后个人中心重新读取 `pending`、`active`、`deleted` 三个列表，而不是局部猜测被影响的条目；聊天页移除该候选并展示结果。两处复用同一个项目内“记忆冲突”弹窗，明确列出新值、现有值和字段名称。

7. **并发保护。** 提交前在仓库事务中再次计算冲突，不能只依赖预检结果。若预检后有新冲突，未携带替换决定的请求仍返回 409；携带替换决定的请求覆盖该事务中所有当前冲突项。

## Risks / Trade-offs

- [更多往返导致确认稍慢] → 预检只读且仅在需要激活时调用；无冲突确认保持一次写请求。
- [并发导致预检过期] → 写事务内重新检查，以 409 或显式替换确保不会静默丢失数据。
- [前端只更新新项目再次陈旧] → 个人中心统一重新加载三列，聊天页按候选编号移除并显示服务端结果。
- [字段别名留下重复历史] → 新写入标准化、读/比对兼容别名；不做不可解释的批量迁移。

## Migration Plan

1. 先部署 FastAPI 冲突预检与显式确认契约，旧确认调用在存在冲突时获得 409 而不是覆盖。
2. 部署 Spring 代理并保持登录态派生范围。
3. 部署 Vue 冲突弹窗和重试逻辑，完成后再开放所有入口的显式替换。
4. 回滚时保留已有回收站和审计数据；不得以 SQLite 手工删除来恢复自动覆盖行为。
