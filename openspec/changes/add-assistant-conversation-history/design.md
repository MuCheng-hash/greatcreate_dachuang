## Context

LLM 服务已将每次 Agent 会话写入 SQLite 的 `agent_thread` 和 `agent_message`，并通过 `threadId` 支持续聊，但仓库缺少按所有者列出线程的方法，Spring 业务服务也没有历史接口。前端目前将当前线程和渲染消息保存在 `sessionStorage`，只能在同一浏览器标签会话中恢复，不能可靠地跨会话回看。

## Goals / Non-Goals

**Goals:**

- 复用现有 Agent SQLite 数据作为历史记录唯一事实来源。
- 按账号所有者和 `CHAT` 任务类型列出活动会话。
- 加载完整历史消息并继续原线程上下文。
- 提供无需额外模型调用的标题与预览。
- 支持新建空白会话和归档旧会话。
- 在 LLM 和 Spring 两层都执行所有权校验。

**Non-Goals:**

- 不新增数据库或把历史消息复制到 MySQL。
- 不提供历史搜索、重命名、导出或跨账号共享。
- 不恢复工具审计详情、引用结构或逐字流事件，仅恢复可读的用户/助手消息。
- 不为已有教学方案和资源发现线程提供历史界面。

## Decisions

1. SQLite Agent 仓库仍是会话事实来源。新增 `list_threads(owner_id, task_type, limit)`，用首条用户消息元数据中的 `taskType` 筛选 `CHAT`，并通过 SQL 子查询返回首条用户消息作为标题、最后一条消息作为预览、消息数和更新时间。备选方案是在 MySQL 新建历史表，但会造成双写和一致性问题。

2. 标题取首条用户消息去除多余空白后的前 40 个字符，预览取最后一条消息前 80 个字符。标题与预览均在服务端确定，避免每个客户端重复规则，也不产生 LLM 成本。

3. FastAPI 提供内部的线程列表、线程详情和归档接口；Spring 提供同源的认证接口，并从当前用户计算 `ownerId`，绝不接受浏览器提交的 owner。详情接口同时传入当前学校范围，复用 `require_thread` 的 owner/scope 校验。

4. 前端侧栏显示最近 50 个活动会话。选择历史项时先读取详情，成功后替换当前消息与 `threadId`；发送新问题继续原线程。新建会话只清空本地当前状态，首条新消息发送时由服务端创建线程。

5. 归档作为可恢复数据操作，只把状态改为 `archived` 并从活动列表移除，不物理删除消息。归档当前会话后前端自动进入新会话状态。

## Risks / Trade-offs

- [旧线程没有 `taskType` 元数据] -> 不纳入智能问答历史，避免混入其他任务；新旧问答主流程已写入该字段。
- [历史消息不包含原引用的完整展示结构] -> 恢复用户与助手正文，后续新回答仍正常返回引用。
- [历史列表与刚完成的流式响应短暂不同步] -> 最终事件后重新加载列表。
- [恶意用户猜测 threadId] -> FastAPI 查询必须同时匹配服务端计算的 owner 和学校 scope。

## Migration Plan

无需数据库迁移。先部署向后兼容的 LLM 列表查询，再部署 Spring 历史接口和前端；回滚前端或 Spring 不影响现有线程数据与问答流程。
